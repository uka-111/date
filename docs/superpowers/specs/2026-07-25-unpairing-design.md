# 取消配对设计说明

## 目标

为双方约会日历增加“取消配对”功能。取消后保留历史内容；如果原来的两个人以后重新配对，则恢复这段旧关系和旧内容。如果与新对象配对，则使用全新的共享空间。

## 用户可见行为

1. 在配对管理区域显示“取消配对”按钮。
2. 按钮使用危险操作样式，并在移动端保持易点击。
3. 点击按钮后显示二次确认弹窗，说明：
   - 当前配对关系将结束；
   - 历史日历、预约、照片和文字记录保留在云端；
   - 取消后双方暂时不能查看这段共享内容；
   - 以后需要重新创建或加入新的配对。
4. 确认成功后立即清除当前会话中的配对状态，并回到配对入口页。
5. 取消过程中失败时保留当前页面，显示可理解的错误提示，允许重试。

## 数据模型

不删除 `couples`、共享数据或照片对象，避免历史记录因级联删除而丢失。

在 `couple_members` 增加 `left_at timestamptz`：

- `NULL` 表示当前成员仍处于有效配对中；
- 有时间值表示该成员已退出旧配对。

将原先“每个用户只能存在一条成员记录”的约束调整为“每个用户只能有一条有效成员记录”。这样用户退出旧配对后，可以加入或创建新的配对，同时旧关系和历史数据仍可保留。

为识别原来的两个人，保留旧 `couples` 及两条历史成员记录，并在重新兑换邀请时按双方用户 ID 查找已结束的旧 couple：

- 找到匹配的旧 couple：把双方的 `left_at` 恢复为 `NULL`，恢复旧共享内容；
- 找不到匹配的旧 couple：创建新的 couple，只能看到新的共享空间；
- 不允许把某个用户与第三人配对后看到原来两人的旧内容。

## 数据库接口

新增安全 RPC：`leave_current_couple()`。

- 只允许当前登录用户操作自己的成员记录；
- 将当前用户的 `left_at` 设置为当前时间；
- 不删除 `couples` 或任何共享数据；
- 返回成功状态，供前端刷新会话；
- 重复调用应安全返回，不产生重复数据或异常。

所有共享数据的 RLS 继续通过“当前用户存在有效成员记录（`left_at IS NULL`）”判断访问权限。退出后，旧共享内容立即对双方隐藏，但数据库中的历史记录仍然存在。

## 前端结构

- `AuthGateway` 增加 `leaveCurrentCouple()` 方法。
- Supabase 网关调用新增 RPC，并在成功后重新读取会话/配对状态。
- `SessionProvider` 在操作成功后把当前配对状态更新为空。
- `PairingScreen` 或配对管理卡片加入按钮、确认弹窗、加载状态和错误状态。
- 退出后显示重新配对入口，而不是继续显示旧日历。

## 安全与边界

- 未登录用户不能调用成功的退出 RPC。
- 用户不能替其他用户退出配对。
- 退出不会删除照片、预约、日记或通知数据。
- 重新配对时，原来的两个人恢复旧有效成员关系；与新对象配对时创建新的有效成员关系。
- 手机 VPN 访问问题不在本功能范围内；当前公网部署在手机开启 VPN 时可以使用，免 VPN 访问需要另行更换网络/托管方案。

## 验收标准

1. 已配对用户能看到取消配对按钮并完成二次确认。
2. 取消成功后双方都回到配对入口，不能继续访问旧共享内容。
3. 数据库中的旧预约、日历、照片和文字记录仍存在。
4. 原来的两个人重新邀请配对后能看到旧内容；与新对象重新配对时看不到旧内容。
5. 重复点击、网络失败和未登录调用都有明确且安全的结果。
6. 自动化测试覆盖 RPC、RLS 和前端状态更新。
