# Supabase 双人云端同步设计

## 背景

当前应用把身份、预约、空闲时间、通知、日记和照片保存在单个浏览器中。该版本适合本地体验，但两台手机不能共享数据，也没有正式账号和数据库权限。

本阶段将应用升级为仅供两名成员使用的在线版本。用户已确认使用 Supabase、两个独立邮箱账号、持久登录、一次性配对邀请码、全量结构化数据同步、照片同步，并且不导入当前浏览器中的本地测试数据。

## 范围与阶段

本设计覆盖一个完整的云端版本，但按以下顺序交付：

1. 数据库结构、数据库函数、RLS 权限和私有照片桶。
2. 邮箱账号、长期登录、创建共享空间和邀请码配对。
3. 空闲时间、约会、调整、通知、日记和偏好的云端读写与实时刷新。
4. 照片压缩、上传、浏览和删除。
5. Vercel 部署、Supabase Auth 回调配置和双账号验收。

当前 SQL Editor 在设计和迁移文件经过审查前保持空白，避免在生产项目中执行未经版本控制的临时代码。

## 身份验证与会话

- 两名成员分别使用自己的邮箱和密码注册。
- 邮箱必须通过 Supabase Auth 验证后才能创建或加入共享空间。
- 登录会话默认持久化并自动刷新。关闭网页或浏览器后，下次访问通常直接恢复登录。
- 登录页提供“保持登录”开关，默认开启。关闭时仅在当前浏览器会话中保留登录。
- 主动退出、清除浏览器数据或安全状态失效后需要重新登录。
- 配对完成后，账号与 `him` 或 `her` 身份永久关联；应用不再显示手动身份选择入口。
- 密码、数据库密码、`service_role` 和 secret key 不进入前端代码、Git 或 Vercel 前端环境变量。

## 双人空间与邀请码

第一个完成注册的用户创建共享空间并选择自己的身份。系统为该空间生成一次性邀请码：

- 邀请码由数据库安全生成，具备足够随机性。
- 数据库只长期保存邀请码摘要，不保存可重新读取的明文。
- 明文邀请码只在生成或重新生成时返回给创建者。
- 邀请码有效期为 7 天。
- 第二个已验证账号输入邀请码后加入共享空间，并自动获得相反身份。
- 使用成功后邀请码立即失效。
- 过期或未使用的邀请码可由已有成员重新生成，新邀请码会使旧邀请码失效。
- 一个共享空间最多有两个成员；第三个账号不能加入。
- 配对、邀请码校验和成员写入通过数据库事务函数执行，避免并发加入导致超过人数限制。

## 数据模型

### 核心表

- `profiles`：账号公开资料、显示名称和创建时间，主键关联 `auth.users.id`。
- `couples`：共享空间、创建者、创建时间和更新时间。
- `couple_members`：空间成员、账号 ID、`him`/`her` 身份和加入时间；每个账号只能属于一个空间，每个空间每种身份只能出现一次。
- `couple_invites`：邀请码摘要、有效期、使用时间和创建者。
- `availabilities`：成员、日期、多个时段、备注和更新时间。
- `invitations`：发起方、接收方、日期、多个时段、多个活动、备注、状态和时间戳。
- `invitation_events`：不可变的邀请历史，记录操作人、动作、备注及建议日期、时段和活动。
- `notifications`：接收者、邀请、类型、创建时间和已读时间。
- `daily_notes`：空间、日期、标题、正文、创建者和更新时间；同一空间同一日期最多一条。
- `daily_photos`：空间、日期、上传者、私有存储路径、文件类型、尺寸、排序和时间戳。
- `user_preferences`：用户自己的日历尺度等界面偏好。

所有共享业务表都显式包含 `couple_id`，便于权限判断、索引和查询。日期使用 `date`，时间戳使用带时区的 `timestamptz`，时段与活动使用受校验的数组或枚举值。

### 数据完整性

- 外键使用明确的删除策略；删除账号不会无意删除另一名成员的全部共享历史。
- 空闲时间对 `couple_id + owner_id + date` 建唯一约束。
- 邀请状态和事件动作使用受约束值。
- 数组不能为空且不接受空字符串；日期、发送者、接收者和空间成员关系由数据库验证。
- 约会创建、状态变更、历史事件和通知通过事务型数据库函数完成，避免只写入部分记录。
- 客户端继续保留领域规则用于即时反馈，数据库是最终权限和一致性边界。

## 权限与安全

所有业务表和照片存储均启用 Row Level Security：

- 未登录用户不能读取或修改任何共享数据。
- 已登录用户只能读取自己所属 `couple_id` 的数据。
- 写入时数据库验证操作者确实是该空间成员，并校验记录中的成员 ID。
- 通知只能由接收者标记已读。
- 用户偏好只能由该用户本人读写。
- 邀请码不能通过普通 `select` 查询；创建、重新生成和兑换只能调用受控 RPC。
- 约会状态变更不能由任意 `update` 绕过角色和状态机规则。
- 照片桶为 private，路径格式为 `<couple_id>/<date>/<uuid>.<ext>`；Storage 策略验证首段空间 ID 与当前成员关系。
- 前端只使用 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_PUBLISHABLE_KEY`。

## 客户端架构

### 会话层

现有 `SessionProvider` 从手动 `PartnerId` 切换为 Supabase Auth 会话。它负责：

- 恢复持久会话并监听登录状态变化。
- 加载当前用户的 `profile` 和 `couple_members` 记录。
- 区分登录、待邮箱验证、未配对、已配对和加载失败状态。
- 从成员记录派生 `PartnerId`，不接受客户端任意切换。

### 数据仓库层

现有 `DateBookingRepository` 保持为页面与存储之间的边界，但接口升级为异步操作。新增 Supabase 实现，负责：

- 将数据库行映射为现有领域模型。
- 调用 RPC 完成邀请创建、确认、拒绝、调整、接受调整和取消。
- 查询空闲时间、安排、通知、日记和偏好。
- 订阅当前空间的实时变化，并触发页面重新获取一致数据。
- 将 Supabase 错误转换为稳定的中文错误类型。

测试继续使用内存或本地假仓库，不依赖生产 Supabase 项目。旧 `localStorage` 数据不会自动上传；第一次在线登录显示空白云端空间。旧本地仓库仅保留给迁移期测试或明确的本地开发模式，不能与云端数据自动合并。

### 加载与失败状态

- 首次加载显示明确的加载界面，不把“还没读取”显示为“没有安排”。
- 写操作成功前不显示成功提示。
- 网络失败时保留表单内容并提供重试。
- 第一版不支持离线编辑；断网时已加载内容仍可查看，但修改入口会提示需要恢复网络。
- 实时订阅断开后自动重连，并在重连后重新获取服务器快照。

## 照片同步

- 使用 Supabase private Storage bucket。
- 每个空间每个日期最多 30 张照片，上传前后都校验数量限制。
- 客户端上传前将图片缩放到合理长边并压缩，减少移动流量和存储占用。
- 支持 JPEG、PNG 和 WebP；HEIC 先在客户端尝试转换为兼容格式，失败时显示明确提示而不是上传不可预览文件。
- 上传流程先写入私有文件，再写 `daily_photos` 元数据；元数据写入失败时删除刚上传的孤立文件。
- 删除通过受控操作同时处理数据库记录和存储对象。
- 页面使用短时签名 URL 展示照片，不把 bucket 改成公开访问。
- 上传显示逐文件进度、成功数量、失败原因和重试入口。

## 部署

- Vercel 连接 GitHub 仓库的 `master` 分支。
- Vercel 环境变量只包含 Supabase Project URL 和 publishable key。
- Supabase Auth 的 Site URL 与 Redirect URLs 包含生产域名和本地开发地址。
- 每次合并到 `master` 自动构建和部署；预览部署使用独立允许的回调 URL。
- 首次正式验收使用两个真实邮箱账号和两台设备完成。

## 验证策略

### 应用测试

- 注册、邮箱验证提示、登录、会话恢复、退出和非持久会话。
- 创建空间、生成邀请码、7 天过期、单次兑换、邀请码重置和第三人拒绝。
- 两个账号间同步空闲时间、预约状态、通知、日记、偏好和照片。
- 创建邀请及每个状态转换的原子性与历史完整性。
- 加载、失败、重试、实时重连和未配对状态。
- 手机端长活动、长备注、照片进度及无横向溢出。

### 数据库与权限测试

- 匿名用户无法访问业务表和私有照片。
- A 空间成员无法读取或修改 B 空间数据。
- 一名成员不能冒充另一身份或把记录写入其他空间。
- 通知、邀请状态和邀请码只能通过允许的路径变更。
- Storage 路径和 `daily_photos` 元数据保持一致。

### 手工验收

1. 账号 A 注册、验证邮箱、创建空间并生成邀请码。
2. 账号 B 注册、验证邮箱并在 7 天内兑换邀请码。
3. 两台设备分别登录，关闭浏览器后重新打开仍保持登录。
4. 双方完成空闲标记、发起约会、调整、确认和通知已读。
5. 双方在同一日期编辑日记、上传、查看和删除照片。
6. 第三个测试账号和匿名浏览器确认无法访问该空间。

## 明确不做

- 不导入现有浏览器中的本地测试数据。
- 不开放多人群组或超过两名成员的空间。
- 不在第一版支持离线写入和冲突合并。
- 不加入付费、公开分享、社交搜索、短信登录或自建后端服务器。
- 不把 Supabase service role、数据库密码或 secret key放入前端。
